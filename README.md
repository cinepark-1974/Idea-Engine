### [2] 직업 감지 정밀도 — 스코어링 + 상위 N 제한

**진단** — `detect_profession_category()`가 카테고리당 첫 키워드 히트에서 `break`하고 무제한 누적하는 구조였다. LOCKED에 '카페'·'축가' 같은 단어가 하나만 섞여도 카테고리가 붙었다.

「연애의 끝」 실측: **5개 카테고리 동시 감지, LOCKED 블록 20,584자.** 정작 핵심 직군의 디테일이 희석된다.

**변경** — 점수 = Σ(매칭 키워드 길이). 긴 키워드일수록 신뢰도가 높다는 전제.

1. 1위 점수 대비 `min_ratio`(기본 0.3) 미만 카테고리 제거
2. 상위 `max_categories`(기본 3)개로 제한
3. 동점 시 `PROFESSION_KEYWORDS` 등록 순서 유지

**검증 — 「연애의 끝」**

| 카테고리 | 점수 | v2.7.1 | v2.7.2 |
|---|---|---|---|
| 예식웨딩직 | 8 | 포함 | 포함 |
| 법률직 | 5 | 포함 | 포함 |
| 요식서비스직 | 2 | 포함 | **탈락** (문턱 2.4) |
| 엔터테인먼트 | 2 | 포함 | **탈락** |
| 예술전통 | 2 | 포함 | **탈락** |

기존 예시 회귀 없음 — `대기업 재무팀 과장` → 금융기업직 / `쿠킹 스튜디오 오너 셰프` → 요식서비스직 / `의사이자 소설가` → 언론창작직·의료직 / `마약사건 담당` → (매칭 없음, 오매칭 방지 유지).

**추가 수정 — 검증 중 발견** — 스코어링을 넣었는데 LOCKED 블록이 오히려 커졌다. 원인은 `prompt.py`의 주입부가 **LOCKED 42줄을 한 줄씩 개별 스캔해 합집합으로 누적**하는 구조였던 것. 줄마다 상위 3개가 뽑히니 카테고리가 불어나고, 1위 대비 문턱도 줄 단위로만 적용되어 무력해진다. 전체 텍스트를 하나로 합쳐 1회만 감지하도록 고쳤다.

| 지표 | v2.7.0 실측 | v2.7.2 |
|---|---|---|
| 주입 카테고리 | 5개 | **2개** |
| LOCKED 블록 | 20,584자 | **10,733자** |
| 핵심 직군 유지 | — | 예식웨딩직·법률직 모두 유지 |

**하위 호환** — `max_categories=0, min_ratio=0`이면 v2.7.1과 동일 동작. `with_scores=True`로 점수 튜플을 받을 수 있다(디버깅용).

## v2.7.1 패치 (2026-08-03) — Format Authority + 개발 중 포맷 확정

### 발견 경위 — Mr. MOON 질의 2건

> ① "아이디어 엔진에서 포맷이 넘어올 때 내가 옵션을 선택한 경우 그게 우선이 되나?"
> ② "아이디어를 받아 크리에이터 개발하면서 포맷을 확정할 수 있나?"

### 진단 ① — 두 층위가 갈려 있었다

| 층위 | 승자 | 근거 |
|---|---|---|
| 필드 저장 | 작가의 선택 | `main.py` 4496행. 시드는 selectbox 기본 인덱스만 결정 |
| 비트 구조 계산 | 작가의 선택 | `get_beat_structure()`는 `project["format"]`만 참조 |
| **LLM 생성 내용** | **LOCKED** | `build_system_core()`에 `fmt` 미전달 |

`build_system_core()`의 시그니처에 `fmt` 파라미터 자체가 없었다. 포맷이 등장하는 곳은 유저 프롬프트의 `포맷: {fmt}` **한 줄뿐**이었다.

반면 같은 프롬프트에 들어가는 `locked_block`에는 v2.5.2 4대 보호 카테고리 규칙이 붙는다.

> "이 결정 사항들을 절대 재해석·약화·우회·생략하지 마라."

**라벨 한 줄 대 절대 준수 명령.** LLM이 어느 쪽을 따를지는 정해져 있었다. 「상속」·「연애의 끝」 2건 연속 재발했고, 두 작품 모두 상류가 시리즈로 넘겼으나 작가 판단은 영화였다.

### 진단 ② — 확정 시점이 판단 시점보다 앞서 있었다

- `project["format"]` 대입 지점이 전 코드에 **단 한 곳** — 프로젝트 생성 버튼 내부. 이후 변경 UI 부재
- **"미지정"은 보류가 아니었다.** `get_beat_structure()`가 "시리즈"·"미니"가 없으면 영화 구조로 폴백 → 미지정 = 묵시적 영화 확정. 웹툰·웹소설·숏폼·다큐·애니도 동일
- 포맷 적합성 판정 기능 부재(`format_fit` 계열 필드 0건). Brainstorm은 `fmt`을 **입력으로 받아** 카드를 만든다 — 포맷이 이미 정해졌다는 전제 위에 서 있었다
- 그러나 포맷 판단은 **사건 밀도·인물 수를 봐야 굳는** 성질이며, 이는 Brainstorm·Core를 본 뒤에야 가능하다

### 변경

**① `get_format_authority_block(fmt)` 신설 — `prompt.py`**

확정 포맷을 LOCKED보다 상위로 선언한다.

> 이 값은 작가가 UI에서 직접 확정한 것이며, 이 작품의 모든 설계에 우선한다. ★ LOCKED 항목보다 상위다. ★
> LOCKED나 아이디어 원문에 다른 포맷 표현이 남아 있다면 상류의 잔재이므로 무시하라.

무시한 사실은 `format_conflict_note` 필드로 보고하게 한다. 영화면 "회차·시즌·EP 표현 금지", 시리즈면 회차 훅·장기 서사선을 요구한다.

**예외 범위를 블록 말미에 명시** — 이 규칙은 포맷 항목에만 적용되며, 결말 형식·음악 규약·시각 모티프 등 나머지 LOCKED의 절대 보존 원칙은 불변이다.

**② 주입 지점 4곳** — `build_system_core()`에 `fmt` 파라미터 추가(디폴트 `""`), Character Bible·Treatment·Tone Document에도 연결. 이 셋은 이미 `fmt`을 받고 있었으나 라벨로만 쓰고 있었다.

**③ STEP 1 포맷 확정·변경 UI 신설 — `main.py`**

- 개발 중 언제든 포맷 변경 가능
- LOCKED 내 포맷 어휘(부작·회차·시즌·회당·EP·러닝타임 등) 자동 감지 → 시리즈/단편 성격이 어긋나는 항목만 충돌로 표시 + **[충돌 LOCKED 항목 제거]** 버튼
- 영화 ↔ 시리즈 전환이면서 `structure_story`가 이미 있으면 Structure 재실행 권고

**④ Structure 진입 시 미지정 차단**

`st.stop()`으로 진행을 막고 포맷 확정 화면으로 이동시킨다. 조용한 영화 폴백을 제거했다.

**⑤ Brainstorm 분석에 `format_fit` 축 신설**

| 필드 | 내용 |
|---|---|
| `current_format` | 작가가 확정한 포맷 |
| `recommended_format` | 소재 자체가 요구하는 포맷 |
| `match` | 일치 여부 |
| `event_density` | 소재가 지탱할 수 있는 사건 수와 밀도 |
| `character_load` | 축이 되는 인물 수와 요구 분량 |
| `rationale` | 판단 근거 |
| `if_forced` | 확정 포맷 유지 시 무엇을 조정해야 하는가 |

**권고이지 판정이 아니다.** 작가의 선택을 바꾸라고 요구하지 않으며, 불일치 시 "이 포맷을 유지하려면 무엇을 조정해야 하는지"로 끝낸다. 판단 근거는 **사건 밀도와 인물 수로 한정** — 흥행성·플랫폼 트렌드를 근거로 드는 것은 금지.

### 하위 호환성

- v2.5.0~v2.7.0 프로젝트 JSON **100% 호환**
- `build_system_core`의 `fmt`은 디폴트 인자 추가이므로 기존 호출부 무수정 동작
- `format_fit` 없는 구버전 분석 결과는 표시만 생략
- 포맷이 "미지정"이면 권위 블록이 빈 문자열 → v2.7.0과 출력 동일

적출 **금지** 항목을 명시적으로 선언 — 장르 관습, 판타지·SF 설정, 작가의 의도적 왜곡, 취향·완성도·흥행성 의견, **"더 재미있을 것 같은 대안" 제시**.

> "확신이 없으면 적출하지 않는다. 오탐 1건이 미탐 1건보다 해롭다."

최대 5건 · severity 3단계(CRITICAL/MAJOR/MINOR) · 각 항목은 [위치·오류·실제·영향·대안 2개·LOCKED 교체안] 구조.

**대안 생성 규칙**: 원 LOCKED가 노린 극적 기능(오브제 연결·인물 대비 등)을 반드시 유지해야 한다. 기능을 바꾸는 대안은 제시 금지.

**② `prompt.py` — Profession Pack 주입부에 `institutional_reality` 연결**

`build_locked_block()` 내 블록 생성부에 조건부 출력 추가. 해당 필드를 가진 카테고리만 [제도·절차 사실성] 블록을 받는다.

**③ `profession_pack.py` — "예식웨딩직" 카테고리 신설**

세부 직종 8종(사회자·주례·웨딩플래너·예식장 진행 매니저·축가·본식 촬영·드레스숍·커플매니저). `forbidden`에 역할 혼동 오류 8종 명시.

`korea_context` 핵심 조항:

> 사회자가 혼인서약문·성혼선언문 원고를 **대필**해 주는 실무는 실재한다. → '문장을 쓴 사람'과 '문장을 낭독한 사람'은 반드시 구분해서 쓸 것.

**④ `profession_pack.py` — `institutional_reality` 필드 도입**

| 카테고리 | 수록 |
|---|---|
| 법률직 | 가사·이혼 8종 + 절차·윤리 3종 |
| 예식웨딩직 | 역할·효력·계약 5종 |

기존 딕셔너리 리터럴을 수정하지 않고 `INSTITUTIONAL_REALITY` dict를 사후 병합하는 방식 — 나머지 17개 카테고리는 필드가 생기지 않아 출력이 완전히 동일하다.

**⑤ `main.py` — `call_reality_gate()` + Core 뷰 UI**

### 위치 원칙 — Treatment 직전이 아니라 Core 직후

Core 단계에서 이미 로그라인·시그니처 모먼트·엔딩 이미지가 확정된다. Treatment 직전에 검문소를 두면 되돌릴 비용이 너무 크다. **Character Bible 진입 전이 회수 가능한 마지막 지점**이다.

### 작가 주권 원칙

엔진은 적출만 하고 판단하지 않는다. 모든 항목에 '무시' 선택지를 **강제로** 제공한다. 작가가 의도적으로 현실을 비트는 것은 엔진이 차단해서는 안 되는 영역이며, 이는 LOCKED 절대 보존 원칙과 동일한 근거에 선다.

#### ① 시퀀스 사이클 사전 설계 (Action Cycle Design)

**문제:** Writer가 비트 단위로 사이클 반복을 감지해도, 씬 플랜이 이미 루프 구조로 짜여 있으면 변주 여지가 좁다.

**처방:** Treatment 비트 스키마에 `action_cycle` 필드 신설. Beat 6~12 구간에서 의무 작성.

- 공간 시퀀스 4단계 분해: `[시작 공간 → 사건 공간 → 외부 조력 공간 → 복귀 공간]`
- 동일 사이클 패턴 3회 이상 반복 → 자동 경고
- 같은 외부 공간 + 같은 조력자 만남 3회 이상 → 자동 경고
- 사이클 변주 4기법 처방: 순서 역전 / 압축 / 차단 / 침범

**구현 위치:**

#### ② 적대자 능동성 설계 (Antagonist Active Action)

- `antagonist_active_actions_per_beat` 필드: 비트별 능동 행위 1개 명시
- 수동 회피(침묵·외면) ≠ 적대 행위 — 절대 룰 명문화
- 적대자 아크 3단계 격상 강제: 1막(은폐자) → 2막(능동 방해자) → 3막(직접 충돌자)

**구현 위치:**

**문제:** 도입된 명명 인물·소품이 회수되지 않음. 비트 집필 단계에서는 발견 어려움.

- 명명 인물(고유명사 부여 조연 이상) + 명명 소품(서사적 의미) 자동 리스트화

## v2.5.4 핫픽스 (2026-05-13) — Treatment Build JSON 출력 안정화

### 진단 — 운영 중 발견된 회귀 결함

v2.5.3 적용 후 Treatment Build 단계에서 캐릭터 바이블과 동일한 JSON 파싱 실패가 발생. 실제 에러:

```
Treatment 2막 실패: Invalid control character at: line 15 column 31 (char 2443)
```

원인 — narrative 필드(2500~4000자 긴 줄글)에 모델이 자연스럽게 줄바꿈(`\n`) / 탭(`\t`) / 캐리지리턴(`\r`)을 넣어버려 JSON 파싱 실패. v2.5.1에서 캐릭터 바이블에 적용했던 강제 JSON 출력 룰이 Treatment Build에는 적용되지 않은 회귀.

자동 재시도가 있었지만 1회뿐이고 룰이 약해 다시 실패하는 패턴.

### 축 1: TREATMENT_BEAT_RULES_TEMPLATE에 9개 강제 JSON 출력 룰 신설

캐릭터 바이블 v2.5.1과 동일 패턴으로 강화.

| # | 룰 | 효과 |
|---|---|---|
| 1 | 단일 JSON 객체 (설명·주석·마크다운 펜스 금지) | 코드 펜스 출력 차단 |
| 2 | 모든 key는 쌍따옴표 | key 누락 차단 |
| 3 | 모든 string value는 쌍따옴표 | value 누락 차단 |
| 4 | string value 안의 인용은 작은따옴표만 | 쌍따옴표 충돌 차단 |
| 5 | **string value 안에 줄바꿈/탭/캐리지리턴 절대 금지** | **이번 실패의 직접 원인 차단** |
| 6 | string value 안에 역슬래시 금지 | 이스케이프 깨짐 차단 |
| 7 | 후행 쉼표(trailing comma) 금지 | 파싱 실패 차단 |
| 8 | ```json 펜스로 감싸지 말 것 | safe_json_loads 호환 |
| 9 | 출력 시작 `{` / 출력 끝 `}` | 전후 텍스트 차단 |

**Treatment 특수 주의 — narrative 필드** 섹션을 별도로 명시:

> narrative는 트리트먼트에서 가장 긴 string value (2500~4000자). 이 안에 자연스럽게 줄바꿈을 넣으면 안 된다.
> - 단락 구분이 필요하면 마침표 + 공백으로만 처리
> - 대사 인용이 필요하면 작은따옴표만 사용
> - 특수 문자(`\n`, `\t`, `\r`)를 텍스트로도 쓰지 마라
> narrative 한 필드의 실패가 Treatment 전체를 무너뜨린다.

**자가 검증 5항목** — 출력 직전 모델이 스스로 점검.

### 축 2: call_treatment_beats 강화 — 스트리밍 + 2회 자동 재시도

기존: 1차 시도(temp 0.4) → 1회 재시도(temp 0.3) → 실패 시 빨간 에러.

v2.5.4: 1차 시도(temp 0.4) → **1차 재시도(temp 0.2)** → **2차 재시도(temp 0.05 + JSON_OUTPUT_RULES_STRICT 주입)** → 마지막에도 실패 시 **제어 문자 사후 정리 안전망**.

| 단계 | temperature | 강조 메시지 | 변경 |
|---|---|---|---|
| 1차 시도 | 0.4 | 기본 + v2.5.4 룰 | 스트리밍 전환 |
| 1차 재시도 | 0.2 | 제어 문자 금지 강조 | 스트리밍 + temp 강화 |
| 2차 재시도 | 0.05 | STRICT 룰 주입 | 스트리밍 + 최저 temp |
| **안전망** | - | 사후 처리 | **string value 내부 제어 문자를 공백으로 치환 후 재파싱** |

3개 호출 모두 `client.messages.create()` → `client.messages.stream()`로 전환해 long requests 정책도 동시 대응 (v2.5.3 적용 패턴).

### 축 3: 제어 문자 사후 정리 안전망 (v2.5.4 신규)

모든 자동 재시도가 실패할 때 마지막 보루로 정규식을 사용해 string value 내부의 제어 문자를 공백으로 치환한 뒤 다시 파싱 시도. JSON 구조의 줄바꿈은 보존하고 string value 안의 것만 처리.

```python
def _clean_control_chars(match):
    s = match.group(0)
    return re.sub(r'[\n\r\t]+', ' ', s)
txt4 = re.sub(r'"(?:[^"\\]|\\.)*"', _clean_control_chars, txt3)
```

대부분의 경우 1~2차 자동 재시도에서 잡히지만, 정말 어려운 케이스에서 이 안전망이 최후의 차단막이 된다.

## v2.5.2 핫픽스 (2026-05-04) — Idea→Creator 인계 LOCKED 추출 확장

### 진단 — 「오랜만에」 검증에서 발견된 결정적 결함

> "Idea Engine에서 아이디어를 제공했을 때 LOCKED를 해도 주요 포인트가 바뀌는데, 이를 방지할 수 있는 방법은 없나?" — Mr. MOON

「오랜만에(가제)」 작품 검증에서 **18개 핵심 모티프 중 11개(61%)가 Creator 출력에서 휘발**되는 현상이 발견되었다. Mr. MOON의 풀버전 아이디어와 Idea Engine 산출물(IdeaDiagnostic)을 Creator JSON과 정밀 비교한 결과, **결함의 원인은 LOCKED 시스템의 강도가 아니라 데이터 인계 구조**임이 명확해졌다.

| 모티프 | Mr. MOON 입력 | Idea Engine 인식 | Creator LOCKED 등록 |
|---|---|---|---|
| 버즈 통화연결음 | ✓ | ✓ ("Hook 점수 9/10 독창성 근거") | ✗ 누락 |
| 노래방·LP 금지 | ✓ | ✓ ("음악 사용 규약 LOCK"으로 명시) | ✗ 누락 |
| 건물 중정 구조 | ✓ | ✓ ("두 타임라인 연결핀 후보") | ✗ 누락 |
| 시드니/런던 외국행 | ✓ | (산출물에 등장) | ✗ 누락 |
| 옛 단체사진 / 노트 발견 | ✓ | ✓ ("Creator 결정 의제로 등록") | ✗ 누락 |

### 축 2: max_tokens 16,000 → 24,000

v2.5.0 신규 4개 필드로 응답 토큰이 평균 2,000~3,000 증가했다. 16,000 한계로는 여유 마진이 부족했음. 24,000으로 상향하여:

- 평균 응답에 충분한 마진 확보
- max_tokens 잘림 자동 재시도(분량 축소 모드) 진입 빈도 감소
- 실제 비용은 평균 사용량 변화 없음 (max_tokens는 한계값일 뿐 평균값이 아님)

### 축 3: JSON 파싱 자동 재시도 1회 → 2회 (temperature 단계적 하강)

기존: 1차 시도(temp 0.3) → 실패 시 1회 재시도(temp 0.2) → 그래도 실패하면 사용자에게 수동 재실행 요청.

v2.5.1: 1차 시도(temp 0.3) → **1차 재시도(temp 0.15)** → **2차 재시도(temp 0.05 + JSON_OUTPUT_RULES_STRICT 추가 주입)** → 그래도 실패하면 raw 디버그 표시.

**Temperature 단계적 하강의 효과**

| 단계 | temperature | 강조 메시지 |
|---|---|---|
| 1차 시도 | 0.3 | 기본 프롬프트 |
| 1차 재시도 | 0.15 | "★ 작은따옴표만 / 줄바꿈 금지 / 역슬래시 금지 / 후행 쉼표 금지 / 코드 펜스 금지 ★" |

## v2.5.0 업데이트 (2026-05-04) — Writer Engine v3.5.1 환류 반영 + 5축 데이터 인터페이스

### 진단 — Writer Engine으로부터의 환류

> "Rewrite가 짚은 8개 결함 중 5개가 Writer Engine 단계가 아닌 Creator Engine 입력 단계의 미비에서 시작된 것으로 판단됨. Creator JSON 입력 자체가 부실하면 Writer 룰셋이 잡지 못하는 결함이 그대로 시나리오에 재현됨."

「오랜만에(가제)」 작품을 Writer Engine v3.3.0으로 집필한 결과 Rewrite Engine 분석에서 **7.1점/10.0(고려 등급)** 측정. Writer Engine은 v3.5.1로 자체 보강(A19 시간 표기 금지, A25 캐릭터 보이스 차별화, A26 중반 침식 차단, A27 POV 회전, OBSTACLE INTENSITY) 완료. 그러나 Writer 단에서 결함을 후처리하는 것은 한계가 있고, **Creator Engine이 출력하는 JSON 구조 자체가 Writer가 흡수할 수 있는 데이터 인터페이스를 갖춰야** 환류 루프가 닫힌다는 결론.

Writer Engine v3.5.1 코드를 점검한 결과 결정적 단서가 발견됨 — `build_scene_plan_prompt()` 함수의 시그니처에 `opening_strategy: str = ""  # ★ v3.6 신규 — Creator Engine 산출물` 라인이 이미 선반영되어 있음. **Writer는 이미 Creator로부터 데이터를 받을 인터페이스를 만들어두고 기다리고 있는 상태.** Creator Engine v2.5.0은 이 인터페이스를 채워주는 사이클.

v2.5.0은 이 공백을 **5축 데이터 인터페이스**로 메운다. 모든 장르에 적용된다 (멜로/로맨스 한정 아님).

### 축 1: OBSTACLE DESIGN — 장벽 시퀀스 사전 설계

이야기는 갈등(Conflict)만이 아니라 장벽(Obstacle)으로 작동한다. 갈등이 "두 의지의 충돌"이라면, 장벽은 "의지가 도달하지 못하게 막는 것"이다. 장벽이 비트 단위로 설계되지 않으면 인물들이 너무 자주/쉽게 만나·대결해·도달해서 긴장 곡선이 평탄해진다.

Rewrite 진단의 "수진이 매일 서점을 방문하는 구조여서 물리적 거리가 없고 장벽이 실제로 작동하는 순간은 S#66~67뿐이다"가 정확히 이 문제. v2.5는 Structure Build 단계에서 장벽을 비트별로 사전 설계한다.

**장벽 4유형**

| 유형 | 정의 | 장르별 작동 예 |
|---|---|---|
| physical | 물리적 거리·격리·봉쇄·체포·이동 불가 | 멜로의 지방 출장, 스릴러의 추적자 막힘 |
| psychological | 자기 제약·트라우마·죄책감·자존심 | 멜로의 마음 문 닫음, 드라마의 화해 거부 |
| status | 사회적 지위·정체 은폐·금지된 관계·계급 | 멜로의 신분 차이, 스릴러의 위장 신분 |
| temporal | 어긋남·엇갈림·데드라인·과거 봉인·시차 | 멜로의 한 발 늦음, 미스터리의 과거 봉인 |

**장벽 작동 원칙 (전 장르)**

| 원칙 | 강제 사항 |
|---|---|
| 장벽 비중 20~30% | 메인 인물이 목표에 도달하지 못하는 비트가 전체의 20~30% |
| Beat 6/10/13 에스컬레이션 | 1막→2막 / Midpoint 직후 / 3막 진입 직전 — 각 단계에서 장벽이 질적 강화 |
| 장벽 유형 다양화 | 한 작품에 최소 2개 이상의 장벽 유형을 교차 |
| 인물 능동성 자극 | 장벽이 새 행동을 촉발해야 함 (장벽 = 행동 다양성 엔진) |

**Structure Build 출력 의무 — `obstacles` 블록**

```json
"obstacles": {
  "barrier_types": ["physical", "status"],
  "barrier_beats": [3, 6, 10, 13],
  "barrier_escalation": {
    "beat_6": "첫 장벽 가시화 — 구체 묘사",
    "beat_10": "장벽 질적 강화 — 구체 묘사",
    "beat_13": "장벽 최고조 — 구체 묘사"
  },
  "barrier_action_response": "각 장벽에 대해 인물이 시도하는 새 행동"
}
```

이 필드는 Writer Engine v3.5.1의 OBSTACLE INTENSITY 모듈이 직접 흡수해 만남 빈도 50% 상한과 Beat 6/10/13 에스컬레이션을 자동 충족시킨다.

### 축 2: CHARACTER ACTIVE DESIRE — 양방향 능동 갈망 강제

캐릭터의 매력은 "수동적 반응"이 아니라 "능동적 추구"에서 온다. Rewrite 진단의 "재원이 '손님이시니까' '커피 드릴까요'를 반복할 뿐 능동적 선택을 거의 하지 않아 멜로 상대역으로서의 매력이 축적되지 않는다"가 정확히 이 문제.

기존 Creator Engine은 주인공의 능동 동기는 잘 잡지만, 상대역(antagonist/ally/mirror, 특히 멜로 카운터파트)이 "주인공이 시키는 일에 반응만 하는 인물"로 전락하는 경향이 있었다. v2.5는 모든 메인 캐릭터에 능동 행동 3개 이상을 강제 명시한다.

**Character Bible 출력 의무 — `active_desire_actions` 필드**

모든 메인 역할(protagonist / antagonist / ally / mirror)에 강제:

```json
"active_desire_actions": [
  "이 인물이 자발적으로 하는 행동 1 — 동기 명시",
  "이 인물이 자발적으로 하는 행동 2 — 동기 명시",
  "이 인물이 자발적으로 하는 행동 3 — 동기 명시"
]
```

**작성 조건 3가지**

| 조건 | 의미 |
|---|---|
| 능동성 | 주인공이 시켜서가 아니라 본인이 자발적으로 하는 행동 |
| 구체성 | "사랑한다", "싫어한다" 같은 추상이 아닌 구체적 동작 |
| 정체성 | 그 행동이 그 인물만의 방식이어야 함 (다른 인물로 대체 불가) |

이 필드는 Writer Engine v3.5.1의 A27(POV ROTATION) 룰셋과 직접 연동된다. A27은 "각 메인 인물의 단독 씬을 최소 2씬 이상 배치"를 강제하는데, 그 단독 씬에서 인물이 무엇을 능동적으로 할지 = 이 필드가 결정한다.

### 축 3: PLANT DISTRIBUTION — 핵심 단서 분산 배치

기존 Plant & Payoff 룰은 "어떤 단서를 심을지"는 잡지만, "언제 어디에 분산 배치할지"는 명시하지 않았다. 결과적으로 핵심 단서가 후반에 몰려서, 그 전까지 관객에게 감정적 근거가 부재한 상태.

Rewrite 진단의 "20년 전 관계의 정체가 S#52~55에서야 암시되고 S#67에서 직접 언급되는데, 그 전까지 관객에게 이 재회가 왜 특별한지 감정적 근거가 주어지지 않는다"가 정확히 이 문제.

v2.5는 모든 Plant 항목에 비트 번호를 강제하고, "관객이 추론할 수 있는 시점(audience_inference_beat)"을 별도 명시한다.

**Core Build 출력 의무 — `planting_payoff` 스키마 확장**

```json
"planting_payoff": [
  {
    "type": "character | relationship | world",
    "plant_description": "심어지는 단서 내용",
    "plant_beat": 2,
    "audience_inference_beat": 9,
    "payoff_beat": 13,
    "payoff_description": "회수 시 의미"
  }
]
```

**분산 배치 강제**

| 권장 분산 | 의미 |
|---|---|
| Plant 1: Beat 1~3 | 1막 초반 (캐릭터 Plant) |
| Plant 2: Beat 3~6 | 1막 중후반 (관계 Plant) |
| Plant 3: Beat 6~9 | 2막 초중반 (세계관 Plant) |

3개 Plant가 모두 같은 비트(±1)에 몰리면 Structure Diagnosis 단계에서 "PLANT 분산 실패" 경고. `audience_inference_beat`이 `plant_beat`과 같으면 "PLANT 노골화", `payoff_beat`과 같으면 "PLANT 추론 시점 부재" 경고.

### 축 4: EMOTIONAL CLIMAX DESIGN — 감정 폭발 지점 사전 설계

Beat Sheet에서 "감정 폭발 비트"가 명시되지 않으면, 한국 영화 특유의 절제·침묵 미학이 과잉 적용되어 폭발 지점이 흐릿해진다. Rewrite 진단의 "감정이 쌓이기는 하나 명확한 폭발 지점이 없다. S#75 고백 장면도 재원의 감정적 반응이 절제를 넘어 부재에 가까워 카타르시스가 약하다"가 정확히 이 문제.

v2.5는 Structure Build 단계에서 폭발 비트 + 폭발 형식 + 감정 온도 변화를 사전 결정한다.

**감정 폭발 7형식 (전 장르)**

| 형식 | 주 적용 장르 |
|---|---|
| confession (고백) | 멜로 / 드라마 |
| confrontation (정면 대결) | 스릴러 / 액션 / 드라마 |
| reveal (진실 폭로) | 미스터리 / 스릴러 / 드라마 |
| parting (결별·이별) | 멜로 / 드라마 |
| breakthrough (자기 돌파·각성) | 모든 장르 |
| sacrifice (희생 결단) | 액션 / 드라마 / SF |
| reconciliation (화해·용서) | 드라마 / 멜로 / 가족 |

**Structure Build 출력 의무 — `emotional_climax` 블록**

```json
"emotional_climax": {
  "beat": 13,
  "form": "confession",
  "pre_temperature": 3,
  "post_temperature": 9,
  "temperature_delta": 6,
  "description": "폭발의 구체적 묘사 2~3문장",
  "genre_alignment": "이 폭발이 장르 약속과 어떻게 일치하는가"
}
```

**핵심 검증** — `temperature_delta`가 4 미만이면 실질적 폭발이 아닌 것으로 판정. Structure Build Gate에서 -1점 감점.

**절제형 엔딩에서도 폭발 1회 강제** — "한국적 절제 엔딩"을 선택해도 Beat 11~13 어딘가에서 폭발 1회는 반드시 일어나야 한다. 절제는 폭발 후의 잔향이지, 폭발 자체의 부재가 아니다.

### 축 5: B-STORY INDEPENDENCE — 서브 캐릭터 독립 동기

서브 캐릭터(supporting / catalyst / subplot_lead)가 "메인 플롯의 보조자·관찰자·공감자"로만 처리되면, 후반에 그 인물이 독립 행동을 하거나 감정을 드러낼 때 뜬금없이 느껴진다. Rewrite 진단의 "서하가 재원의 보조이자 관찰자로 기능하지만, S#81에서 '그분 말고요'라는 대사가 암시하는 서하 자신의 감정이 이전 시퀀스에서 충분히 축적되지 않았다"가 정확히 이 문제.

v2.5는 supporting 역할에 메인 플롯과 별개의 독립 욕망을 강제한다.

**Character Bible 출력 의무 — supporting role 추가 필드**

역할이 supporting / catalyst / subplot_lead / mentor / rival / informant 인 경우:

```json
"independent_desire": "메인 플롯과 별개로 이 인물이 추구하는 것 (1~2문장)",
"active_beat": 8,
"active_beat_description": "그 비트에서의 행동 + 메인 플롯에 미치는 영향"
```

**단순 조력자 패턴 명시적 차단**

| 차단 패턴 | 권장 패턴 |
|---|---|
| ❌ "주인공의 가장 친한 친구. 주인공을 응원한다." | ✅ "주인공의 친구. 자신의 이혼 소송 중 주인공의 사랑을 보며 갈등한다." |
| ❌ "주인공의 동료. 주인공을 돕는다." | ✅ "주인공의 동료. 자기 승진 누락에 대한 분노를 주인공 사건에 투영한다." |
| ❌ "주인공의 가족. 주인공을 걱정한다." | ✅ "주인공의 형. 동생의 성공이 자신의 실패를 증명할까 두렵다." |

이 필드는 Writer Engine v3.5.1의 A26(MIDPOINT EROSION) 룰셋과 연동된다. A26은 "중반(Beat 6~10)에 B스토리가 메인 플롯을 흔드는 사건 최소 1회"를 강제하는데, 그 사건의 동력 = `independent_desire`가 만든 `active_beat`.

## v2.4.2.2 핫픽스 (2026-04-29) — 씨네21 화이트리스트 추가

> "cine21.co.kr은?"

v2.4.2.1까지의 화이트리스트(vkobis / kobis / imdb / variety)는 박스오피스·메타데이터 중심으로 구성되어 있었습니다. 데이터는 정확하지만 **"맥락"**이 빠져 있었습니다. 작가가 차별화 포인트를 도출하려면 박스오피스 수치만으로는 부족하고, **감독 인터뷰·작품 비평·장르 라인업 분석**이 필요한데, 이 영역은 vkobis가 다루지 않습니다.

| **cine21.com** | **씨네21 동일 매체 (대체 도메인)** | **맥락 (신규)** |
| imdb.com | 글로벌 영화·드라마 DB | 데이터 |
| variety.com | 할리우드 산업·신작 보도 | 맥락 |

화이트리스트 4개 → 6개로 확장. 한국 영화 산업 정보가 "데이터 + 맥락" 양면으로 완전해짐. prompt.py의 `get_system_research()` 한국 콘텐츠 검색 가이드도 cine21 명시.

## v2.4.0 업데이트 (2026-04-23) — 시대극 자동 감지 + Period Pack

### 개요

Idea Engine v1.0 시드(`locked_seed`)와 Core Build 결과를 함께 스캔하여 **시대 자동 감지(SAGEUK / COLONIAL / MODERN_HIST)**가 활성화됐습니다. 시대극·일제강점기·근현대사 장르가 감지되면 Period Pack이 자동 주입되어 시대 고증 규칙이 Treatment까지 전파됩니다.

### 추가 기능

- `build_scan_text_for_period_detection()` — 시드+프로젝트 텍스트 통합 스캔 함수 신설
- `_get_period_scan_context()` — main.py에서 시대 감지 컨텍스트 추출 (하위 호환 유지: 시드 없으면 v2.3.10과 동일 동작)
- Period Pack 자동 활성화 — 감지된 시대에 따라 고증 체크리스트, 의상·언어·공간 규칙이 OVERRIDE로 추가
- LOCKED 시드 신호와 연동 — locked_logline·locked_references·locked_genre·locked_theme이 시대 감지의 결정적 시그널로 작동

### 하위 호환성

`locked_seed`가 없거나 시대 키워드가 감지되지 않으면 v2.3.10과 완전히 동일하게 동작합니다. 기존 프로젝트에는 영향 없음.

## v2.3.3 업데이트 (2026-04-21) — 장르별 적대자 유형 재정의

### 진단: 쿠킹클래스 v2.3.2 결과물에서 재확인된 결함

장르 체크리스트가 개선된 v2.3.2에서도 안타고니스트가 여전히 **강회장(아버지)**로 배치되는 현상.

### 원인

`ANTAGONIST_BJND` 모듈 내부에:
1. "모든 적대자(빌런/**아버지**/경쟁자/권력)"라는 문구로 아버지가 적대자 대표 유형으로 명시
2. "쿠킹클래스 강회장 = 이상적 적대자" 예시가 고정 박힘

엔진이 이 학습을 반사적으로 따라 **로맨틱 코미디에서도 부모를 적대자로 배치**.

- **로맨틱 코미디**: Love-Antagonist / Wrong Partner / 내적 결함

  - **부모/가족/권력자는 Catalyst로 분류, 적대자 금지**
- **드라마**: 부모·사회 시스템 가능
- **스릴러**: 직접적 위협
- **호러**: 초자연적 + 공동체 불신
- **액션**: 물리·이념 대립
- **느와르**: 팜므 파탈 + 내면의 어둠

## v2.3.2 업데이트 (2026-04-21) — 장르 기대 체크리스트 강화

### 진단: 쿠킹클래스 v2.3.1 결과물에서 발견된 장르 본질 결함

로맨틱 코미디인데 클라이맥스가 **부녀 화해**로 빠지고, 로맨스 완성은 엘리베이터 전화 한 통으로 꼬리 처리됨. 장르 관객이 기대하는 "로맨스 완성 순간"이 클라이맥스에 없음.

### 원인

`GENRE_FUN_ALIVE` 모듈의 장르 재미 정의가 **한 줄 추상어**로만 제공됨 ("로맨틱 코미디: 어긋남이 웃음과 설렘을 동시에"). AI가 이걸 구체 행동으로 구현할 장치가 없었음.

### 해결 — 장르별 구체 체크리스트

`GENRE_FUN_ALIVE` 모듈을 **11개 장르 각 6~7개 기계적 체크 항목**으로 확장:
- 로맨틱 코미디 / 코미디 / 호러 / 스릴러 / 액션 / 드라마 / 느와르 / SF / 판타지 / 미스터리 / 시대극

각 장르 체크리스트는 **오프닝 / 2막 / 중간 지점 / 클라이맥스 / 엔딩**의 장르별 기대치를 기계적으로 확인.

예시 — 로맨틱 코미디:
- □ 오프닝 3분 안에 주인공의 '사랑/관계 관련 결함'이 행동으로 드러나는가?
- □ **클라이맥스 씬이 '로맨스 완성 순간'인가?** (부녀 화해, 가족 서사 등으로 대체되면 장르 배반)
- □ 웃음 포인트와 설렘 포인트가 각각 최소 5회 이상 배치되었는가?

Core Build JSON 스키마에 `genre_expectation_check` 필드 추가:
- `genre_fun_alive` (true/false)
- `checklist` (항목별 YES/NO + 근거)
- `climax_verdict` (CLIMAX_PASS / CLIMAX_FAIL)

Core Gate 채점 강화:
- `CLIMAX_FAIL` = structure 항목 **-2점**
- `genre_fun_alive: false` = final_score **-1.5점**
- NO 응답 1건당 **-0.5점**

**안타고니스트 구조는 변경 없음** — 장르별 분기가 아니라 모든 장르 공통 모듈 강화로 해결.

## v2.3.1 핫픽스 (2026-04-21)

### 진단: 쿠킹클래스 v2.3.0 결과물에서 발견된 구조적 결함

동일 기획개발보고서 DOCX 내에서 캐릭터 간 설정 모순 발생:

- **유진 백스토리**: "8살 때 어머니 이혼으로 떠남"
- **강회장 백스토리**: "11살 때 아내 위암 사망"

즉 같은 어머니의 생사가 두 가지로 공존. 학력도 "뉴욕 CIA"와 "런던 유학"이 혼재.

### 원인

Character Bible이 캐릭터 4~8명을 순차 생성하지만, 각 호출에서 AI가 Core Build 설정만 참조하고 이전에 생성한 다른 캐릭터의 백스토리는 참조하지 않음.

### 해결 — 캐릭터 일관성 보호 시스템

`prompt.py`에 두 개의 헬퍼 함수 신설:

- **`extract_char_consistency_facts(char_data)`** — 캐릭터 데이터에서 일관성 핵심 사실(나이·직업·가족관계·공유 사건·비밀) 추출
- **`build_prior_chars_consistency_block(prior_chars)`** — 이전 캐릭터들의 핵심 사실을 프롬프트 블록으로 구성

`main.py`의 `call_character_bible()` 순차 루프에서:
1. 캐릭터 1 생성 → 핵심 사실 추출 → `prior_facts`에 저장
2. 캐릭터 2 생성 시 `prior_facts` 블록을 프롬프트에 주입 → 유진 설정과 모순 방지
3. 캐릭터 3 생성 시 `prior_facts`(유진+강회장) 블록 주입 → 누적 일관성
4. (반복)

`CHAR_BIBLE_RULES`에 일관성 규칙 추가: "가족 관계의 생사·이혼 여부, 공유 과거 사건의 시점, 학력·출신지는 단 하나의 버전으로만 존재해야 한다."

## BLUE JEANS NARRATIVE DRIVE (BJND) — 엔진의 척추

### BJND 용어 표준 (전 엔진 공통 어휘)

```
발생요인(Loss/Lack) → 욕망(Desire: Goal+Need) → 해결전략(Strategy) → 대가(Cost)
```

- **Loss(상실)** — 가졌다가 잃은 것. 욕망은 회복/복수/대체로 향함.
- **Lack(결핍)** — 처음부터 없던 것. 욕망은 획득/성장/증명으로 향함.
- **Desire(욕망)** — 외적 Goal(목적) + 내적 Need(필요)
- **Strategy(해결방법)** ★ — 이 인물만의 창의적 해결. **작가의 서명**이 남는 축.
- **Cost(대가)** — 이 전략이 치르게 하는 것. 2막 위기의 원천.

보조 필드: Risk / Ending Payoff / Goal↔Need Gap

### BJND의 끝까지 관통 원칙

BJND는 Core Build에서만 설계되지 않습니다. 전 파이프라인에 강제 전파됩니다.

- **Scene Design**: 각 씬에서 Strategy가 구체적 행동으로 드러남
- **Treatment**: 각 비트에서 Cost 누적 / Strategy 전환 강제
- **엔딩**: Strategy_1 → Strategy_2 전환이 반드시 구현

BJND가 중간에 사라지면 기획서는 강한데 시나리오는 약해집니다.

## v2.3 핵심 — 4축 자가 검증 엔진

엔진이 BJND를 설계한 후, 창작자 관점에서 4축으로 자기 진단합니다.

### ① NECESSITY (필연성)
> "이 인물이 왜 지금 이렇게 살아야만 했는가?"

Lack/Loss가 막연한 설정이면 실패. 구체적 사건·기억·행동으로 인물을 관통해야 합니다.

### ② AUTHENTICITY (인물 고유성) ★ 작가의 서명
> "이 Strategy는 이 인물이 아니면 불가능한가?"

**3중 검증**을 통과해야 합격:
- **치환 테스트**: 다른 작품 주인공에게 붙여도 성립하면 실패
- **유기성 테스트**: 직업 + Lack + Strategy가 한 문장으로 연결되어야 함
- **작가 서명 테스트**: "왜 이 인물은 이렇게 해결하는가"에 작가 시선이 담긴 정당화

### ③ EMPATHY (관객 공감력)
> "관객이 이 인물의 Cost를 보며 자기 자신을 떠올릴 것인가?"

동시대 관객의 보편 상처를 건드리지 못하면 남의 이야기가 됩니다.

### ④ POTENCY (변화 진폭)
> "이 인물의 변화가 관객 마음에 얼마나 큰 흔적을 남길 것인가?"

1막 Strategy_1 → 3막 Strategy_2의 변화가 내적이고 진폭이 커야 관객 마음에 남습니다.

### 종합 자가 진단 — 관객의 얼굴 그리기

4축 설계 후 엔진은 스스로 묻습니다:
1. 관객이 웃을 장면이 구체적으로 있는가?
2. 관객이 가슴 먹먹해질 장면이 구체적으로 있는가?
3. 관객이 '나였다면'을 고민할 장면이 있는가?
4. 영화 끝난 후 관객의 입에 남을 장면이 있는가?

답이 구체적으로 나오지 않으면 캐릭터 재설계.

## OPENING MASTERY (v2.2에서 유지)

첫 3분 안에 관객을 잡지 못하면 영화가 끝입니다.  
2020년 이후 한국 관객은 첫 3분 안에 영화를 판단합니다.

### 오프닝 6기법
- **Action Drop** — 이미 진행 중인 액션 안으로 떨어뜨리기
- **Cold Open** — 본편과 다른 시점/장면으로 시작
- **Tease & Reveal** — 수수께끼 이미지 후 회수
- **In Media Res** — 미래의 결정적 순간 먼저
- **Character Reveal Action** — 주인공을 정의하는 첫 행동
- **Hook Dialogue** — 강렬한 한 줄 대사

### 장르 = 오프닝 DNA

장르 본질이 오프닝의 DNA를 결정합니다.

**복합 장르 법칙**: 두 번째 장르(뒤에 붙은) = 본질
- 로맨틱 **코미디** → 코미디 DNA (첫 3분 웃음)
- 액션 **스릴러** → 스릴러 DNA (첫 3분 긴장)
- 코믹 **로맨스** → 로맨스 DNA (첫 3분 신체 언어)
- 시대극 **액션** → 액션 DNA (첫 3분 물리 쾌감)

### 오프닝 ≠ 도발적 사건

한국 상업영화 표준 3단 구조:
```
오프닝 (0~3분)         = 장르·캐릭터·톤의 선언
Set-Up (3~10분)        = 일상 속 결핍·욕망 축적  
Inciting Incident (10~15분) = 도발적 사건
```

첫 3분에 사건을 터뜨리면 Set-Up이 사라져 관객 공감이 생기지 않습니다.

   테마: 사람은 요리처럼 섞을 수 없다
   엔딩 방향: 한 명 선택 아닌 자기 발견
```

**v2.3부터 OPEN 필드 폐지.** 과거 버전의 OPEN 필드는 "AI가 창작 가능한 영역"이라는 의미였지만, 실제로는 **LOCKED에 없는 모든 것은 이미 창작 가능**합니다. 이중 구조가 혼란만 주었기에 제거했습니다.

**원칙**: 반드시 지킬 것만 LOCKED에 명시하세요. 나머지는 엔진이 자유롭게 창작합니다.

## Planting & Payoff

```
③ Core Build    → planting_payoff 3쌍 설계 (character / relationship / world)
⑥ Scene Design  → 각 장면에 plant_payoff_tag
⑦ Treatment     → 각 비트에 plant_payoff 회수 체크
```

1막에 심은 것이 3막에서 새로운 의미로 회수되어야 합니다.  
회수 없는 Plant = 불만족 / Plant 없는 Payoff = 금지.
